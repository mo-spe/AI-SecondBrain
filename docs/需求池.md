## 可以做了

### 多用户数据隔离与管理员管控
- 痛点：担心多用户数据隔离问题；需要管理员管控能力（权限、内容审核）；没法管理账号
- 方案：RBAC 角色权限体系 + 租户级数据隔离；管理员后台（用户管理、内容审核、资源配额控制）
- 备注：用户增长前的基础设施，越早做越好

## 需要想想

### 用户级 AI 模型供应商与模型选择
- 方向：把全局写死的 AI 服务商/模型配置下沉到用户个人设置，让用户可以为每个 AI 场景独立选择用哪家服务商的哪个模型
- 痛点：
  - 目前 AI 服务商和模型在代码/配置中全局写死，用户无法自主选择
  - 不同用户偏好不同服务商（有人用千问、有人用 DeepSeek、有人用 OpenAI）
  - 用户只有一个 `apiKey` 字段，无法为不同服务商配置不同 Key
  - 所有场景共用同一个模型，无法差异化（如 RAG 问答用贵的、知识提取用便宜的）
- 依赖：无
- 待展开：
  - 数据模型设计：用户 AI 配置如何存储（新表？JSON 字段？），每个场景的 provider+model 映射关系
  - 第一期覆盖哪些服务商：OpenAI / 千问 / DeepSeek / Anthropic / Gemini / Kimi / 智谱 等，优先级
  - 场景粒度：是否需要所有 14 个场景都独立配置，还是归类为几个大类（对话类、生成类、提取类、向量类）
  - Embedding 服务如何支持多服务商（目前只支持千问 Embedding API）
  - 设置页面 UI：服务商卡片 + 模型下拉 + API Key 管理 + 场景-模型映射表
  - ChatSessionServiceImpl 独立于 AiService 的问题，需统一调用链路

### 协作共享知识库
- 方向：用户之间共享知识库，支持协作编辑或只读分享
- 依赖：#1 多用户数据隔离与管理员管控
- 待展开：共享范围（只读/可编辑）、权限粒度、多人编辑冲突处理、知识库级别 vs 知识点级别的共享

### 社交功能（评论/点赞）
- 方向：用户之间可以评论和点赞知识点/卡片，增加交流
- 依赖：#1 多用户数据隔离与管理员管控、#2 协作共享知识库
- 待展开：内容可见性机制（公开/好友/私密）、用户关系模型（关注/好友）、通知体系、内容审核策略
