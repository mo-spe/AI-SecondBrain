# 复习业务当前状态梳理

> 更新时间：2026-10-01
> 范围：Spring Boot 后端、网页端 Vue、Android Jetpack Compose 端  
> 目的：说明当前复习业务的真实执行逻辑，区分已实现行为、设计文档中的目标行为，以及当前会影响用户体验的缺口。

## 1. 结论先行

当前复习功能不是没有业务逻辑，而是已经形成了一个可运行的核心闭环：知识点可以生成复习卡片，用户可以获取待复习卡片并提交答案，服务端会判定对错、记录复习日志、更新掌握度、安排下一次复习并发放复习积分。

目前系统处在“旧卡片表兼容 + 工作区题目池/个人副本新模型并存”的过渡阶段。网页端和 Android 端都调用同一组 `/review/*` 接口，但两端消费的数据粒度不同：网页端使用复习概览、统计、题目池和沉浸式答题；Android 端只拉取今日卡片并在本地解析题干和选项。结果是核心业务共享，体验和边界行为并不完全一致。

最需要注意的现状是：

1. 认证是复习数据的前置条件。用户 JWT 过期或未带上时，后端无法得到 `userId`，当前代码应返回 401；此前日志中的 `userId=null` 会让查询得到 0 张卡片，表现为“今天没有复习内容”。
2. `review_card` 与 `review_card_pool + user_review_card` 两套模型同时参与查询、提交和统计，所有复习行为都要走兼容分支。
3. `getTodayReviewCards` 现在统一查询未归档/未删除且已到期的卡片：`status=0` 或历史兼容的 `status=1`，并要求 `nextReviewTime` 为空或不晚于服务端当前时间。
4. 提交答案后卡片保持活动状态，下一次是否出现由 `nextReviewTime` 决定；自动生成任务发现已有卡片时会跳过重复生成，避免同一知识点不断产生新题。
5. 网页端在一次沉浸式复习会话中保留当前队列，完成本轮后再刷新；Android 端继续保留本轮列表。两端都通过提交结果获得下一次时间和掌握度。

## 2. 业务对象和数据来源

### 2.1 旧模型：`review_card`

`review_card` 是早期个人卡片模型，一条记录同时保存题目内容和个人学习进度，主要字段包括：

- `user_id`、`workspace_id`：卡片归属范围；
- `node_id`：关联知识点；
- `question`、`answer`、`card_type`、`difficulty`：题目内容；
- `review_count`、`correct_count`、`incorrect_count`、`mastery_level`、`memory_strength`：学习进度；
- `last_review_time`、`next_review_time`：排期；
- `status`、`deleted`：状态和逻辑删除。

旧数据仍由 `ReviewCardServiceImpl` 查询和提交，目的是兼容存量数据。

### 2.2 新模型：题目池 + 个人副本

新模型拆成两层：

- `review_card_pool`：工作区级题目模板，保存题干、答案、题型、难度和创建者；
- `user_review_card`：用户对题目模板的个人副本，只保存个人复习次数、正确率、掌握度和排期。

工作区中生成卡片时，后端写入题目池，并自动为生成者创建一份个人副本。其他成员通过 `POST /review/pool/{poolId}/join` 创建自己的副本，彼此的进度互不影响。个人空间生成卡片时，可以直接创建 `pool_id = null` 的个人副本。

这与 `docs/prd/workspace-review-card-pool-prd.md` 中的目标设计一致，但当前实现仍保留旧表兼容查询，尚未完成单一数据访问层收口。

## 3. 当前真实业务链路

```text
登录 / 切换工作区
        ↓
认证拦截器从 JWT 写入 userId、workspaceId
        ↓
知识入库或“纳入复习”
        ↓
生成复习卡片（旧表或题目池 + 个人副本）
        ↓
GET /review/today
        ↓
网页端或 Android 展示题目
        ↓
POST /review/submit
        ↓
判定答案 → 更新卡片进度 → 写 review_log → 发放积分
        ↓
计算 nextReviewTime，并同步知识点掌握度
        ↓
刷新今日列表、统计和下一轮复习
```

### 3.1 卡片生成入口

当前有三类主要入口：

1. **确认知识入库时生成**：`PendingKnowledgeServiceImpl.confirmBatch()` 读取 `generateCards` 或待确认记录中的 `needReview`，为每个知识点生成一张自动卡片。
2. **知识页手动纳入复习**：`KnowledgeServiceImpl.toggleNeedReview()` 将知识点设置为复习目标，并在没有现有卡片时生成两张自动选择题；取消时会删除/归档该知识点的卡片。
3. **复习中心批量生成**：`POST /review/generate-all` 为范围内知识点循环生成卡片，每个知识点当前生成两张手动练习卡。

Quartz 旧任务 `ReviewJob` 还会扫描 `KnowledgeNode.nextReviewTime` 到期的知识点并调用自动生成逻辑。这个任务依赖旧的 `review_card` 查询和通知逻辑，和新题目池模型不是完全同一条链路。

### 3.2 获取今日卡片

Controller `GET /review/today` 读取请求属性中的 `userId` 和当前 `workspaceId`，调用 `ReviewCardServiceImpl.getTodayReviewCards()`，然后同时查询：

- `user_review_card`：用户、工作区、`status ∈ {0,1}`、`is_archived=0`，且 `next_review_time` 为空或已到期；
- `review_card`：用户、工作区、`status ∈ {0,1}`、`deleted=0`，且 `next_review_time` 为空或已到期。

两路结果合并后，Controller 只过滤 `question` 为空的脏数据，并按请求参数进行时间或难度排序。

新旧表都可能返回数据，统计接口也会把两边相加。如果迁移期间同一知识点同时存在两种记录，用户可能看到重复题目，统计也可能重复计数。Quartz 自动生成任务仍读取知识点的 `nextReviewTime`，但会先检查该知识点下是否已经有未归档个人副本，避免再次生成重复卡片；真正进入复习队列的时间以个人卡片 `nextReviewTime` 为准。

### 3.3 提交答案

`POST /review/submit` 的请求字段为 `cardId`、`userAnswer`、`duration`。服务端先按 ID 查询 `user_review_card`，查不到再回退到 `review_card`。

对新模型，服务端执行：

1. 校验个人副本的 `userId`；
2. 从题目池读取正确答案和题目内容；
3. 对选择题等内容做字符串忽略大小写、去首尾空格比较；
4. 累加 `reviewCount`，并累加正确或错误次数；
5. 用复习次数和平均正确率计算 `masteryLevel`、`memoryStrength`；
6. 写入 `lastReviewTime`，保持卡片为活动状态；
7. 写入 `review_log`；
8. 调用 `GamificationService.awardReviewPoints()` 发放积分；
9. 更新所有卡片的下一次排期；`generationType=auto` 的卡片额外同步知识点的复习次数、掌握度和下一次时间；
10. 返回 `isCorrect`、`correctAnswer`、`explanation`、提示消息、`nextReviewTime` 和 `masteryLevel`。

旧模型执行同样的进度更新、排期和日志记录，只是直接写回 `review_card`。

### 3.4 排期算法

默认艾宾浩斯间隔在 `EbbinghausServiceImpl` 中为：

| 本次复习后的阶段 | 正确时默认间隔 |
|---|---:|
| 第 0 次后 | 1 天 |
| 第 1 次后 | 7 天 |
| 第 2 次后 | 14 天 |
| 第 3 次后 | 30 天 |
| 第 4 次及以后 | 60 天 |

答错时使用当前阶段间隔的一半，但不会短于 1 天。用户可以在网页端设置 3～8 个递增的间隔阶段；`ReviewPreferenceServiceImpl` 会在下一次答题时读取偏好。当前 `ReviewCardServiceImpl` 的提交逻辑仍直接调用 `EbbinghausService`，需要继续核对个人间隔偏好是否已经接入所有卡片分支。

## 4. 网页端当前行为

网页端入口是 `frontend/src/views/Review.vue`，调用 `frontend/src/api/review.js`。

### 4.1 列表页

页面加载时并行请求：

- `GET /review/today`：复习队列；
- `GET /review/overview`：今日待复习、已完成、准确率、连续天数、记忆持久度和分类统计。

页面提供：

- 我的复习计划；
- 工作区题目池；
- 新卡片、学习中、即将遗忘、已掌握筛选；
- 智能、时间、难度排序；
- 复习设置和知识点指定提醒；
- 空列表时的恢复复习题目操作。

### 4.2 答题页

网页端进入沉浸式答题视图后：

- 选择题选项由 `question` 文本本地解析；
- 简答/填空使用文本输入；
- 提交后展示正确/错误、正确答案和服务返回的解析；
- 本地保存已答题状态，支持上一题、下一题和题号跳转；
- 提交成功后会调用 `loadReviewCards()` 重新加载服务端列表。

提交后不再立即刷新服务端列表，当前沉浸式页面会完成本轮队列；退出或完成本轮后再重新读取到期卡片。这样答题结果、题号导航和队列长度属于同一个会话快照。

### 4.3 网页端的额外能力

网页端已经接入或预留了以下复习周边能力：

- 复习节奏设置；
- 指定知识点提醒；
- 连续复习天数和准确率；
- 复习质量反馈；
- 工作区题目池、加入复习和查看个人计划；
- 游戏化积分与成长统计。

这些能力不代表所有端都已经消费了相同的接口或统计字段。

## 5. Android 端当前行为

Android 端的复习入口主要由：

- `TodayViewModel`：调用 `GET /review/today`，将空列表显示为“今天没有待复习卡片”；
- `ReviewViewModel`：管理本轮卡片、当前题目、输入答案、提交状态和服务端结果；
- `ReviewSessionScreen`：展示题干、选项、答案解析、记住这一点和查看原知识。

### 5.1 加载和认证

Android 的 `NetworkModule` 从 `SessionStore` 读取 JWT，自动加到 `Authorization: Bearer ...`。收到 401 后，会清除与失败请求匹配的 token。工作区切换接口会返回新的 token 和 `workspaceId`，两者一起保存到 `SessionStore`。

Android Debug 包的后端地址通过 `secondBrainApiBaseUrl` Gradle 属性或 `SECOND_BRAIN_API_BASE_URL` 环境变量注入，默认值只用于当前开发机。真机必须使用手机可访问的电脑局域网地址；使用 USB 调试时可以传入 `http://127.0.0.1:8080/api/` 并执行 `adb reverse tcp:8080 tcp:8080`。

因此 Android 复习数据取决于两件事同时正确：

1. 本地保存的 token 未过期；
2. token 中的当前工作区与用户正在看的空间一致。

如果 JWT 已过期，后端不会得到有效用户身份，复习请求应直接失败为 401。此前日志中的：

```text
JWT expired ...
业务异常：请先登录
```

正是认证失效，不是“数据库没有复习卡片”。早期代码曾把无效身份继续带到查询层，产生 `userId=null` 和 `Total: 0`，这会掩盖真正的登录问题。

如果界面显示 `failed to connect to ...:8080 after 15000ms`，则请求还没有到达 Spring Boot，通常是 Debug 包中的 API 地址失效、手机与电脑不在同一网络，或 Windows 防火墙没有放行 8080；这与知识库为空或 JWT 过期是两类不同问题。

### 5.2 答题交互

Android 当前将 `ReviewCard.question` 当作可能混有选项和解析的历史文本，由 `ReviewPrompt.kt` 在本地解析题干、A-H 选项和解析区域。提交请求只发送卡片 ID、用户答案和答题耗时，解析和正确答案依赖后端返回的 `ReviewResult`。

这使 Android 可以在服务返回后展示解析，但它没有使用网页端的 `overview`、`nextReviewTime`、`masteryLevel`、`reviewCount` 等字段，也没有独立的题目池入口。当前 Android 是“轻量今日复习客户端”，不是完整的复习中心。

### 5.3 与网页端的差异

| 能力 | 网页端 | Android 端 | 当前影响 |
|---|---|---|---|
| 今日卡片 | `/review/today` + 概览 | `/review/today` | 核心数据源相同，但认证/工作区异常会同时影响两端 |
| 统计 | 概览、准确率、连续天数、分类 | 未消费概览 | Android 首页可能无法解释“为什么是 0 张” |
| 答题解析 | 服务解析 + 网页本地题干解析 | 服务解析 + Android 本地题干解析 | 历史题目文本格式变化时，两端可能解析不同 |
| 提交后刷新 | 提交后立即重新拉列表 | 本轮保留内存列表，重新进入再拉 | 同一后端状态问题会表现成不同队列行为 |
| 题目池 | 已有列表、加入、查看个人计划 | 未接入 | 工作区复习体验不一致 |
| 复习设置/提醒 | 已有网页入口 | API 模型存在，页面能力较少 | 偏好和提醒的移动端闭环不完整 |
| 原知识回看 | 可从网页题目关联知识点 | 结果后支持查看原知识 | Android 体验相对完整，但依赖 `nodeId` 返回 |

## 6. 当前阶段已确认的问题

### P0：认证失效会被误认为没有复习内容

复习接口依赖 JWT 中的用户身份和当前工作区。过期 token 会返回 401；如果客户端没有正确处理，页面可能落到空态或通用“加载失败”。这解释了日志中 `userId=null`、两张表查询总数为 0 的现象。

### P0：卡片状态与到期时间曾经没有形成一致的队列规则

本轮已统一为“状态表示生命周期、时间表示是否到期”：提交后卡片保持活动状态，查询同时过滤活动状态和到期时间，掌握度高的卡片仍会按间隔重新出现。

### P1：新旧表并行查询会带来重复和统计口径差异

列表、待复习数量、已完成数量、准确率和连续天数都分别查询新旧表并相加。存量迁移、重复生成或旧任务继续写入时，可能出现重复题目、数量偏大或同一知识点进度不一致。

### P1：新旧表并行统计仍需后续收口

`ReviewJob` 的每日提醒已经同时读取新旧两套卡片并合并到用户级数量，周报和部分历史统计仍主要基于旧表。迁移期间同一知识点同时存在两种记录时，列表和统计仍可能重复，后续需要统一数据访问层。

### P1：网页端与 Android 端的复习上下文仍不完全一致

网页端已经在本轮会话内固定队列，Android 端仍是轻量今日卡片客户端；两端都能拿到下一次时间和掌握度，但 Android 还没有完整的复习概览和题目池入口。

### P1：Android 端缺少复习业务上下文

Android 当前卡片模型只保留 ID、知识点、题目、答案和题型，没有消费掌握度、复习次数、下次时间和概览统计。因此用户无法在移动端判断卡片为什么今天出现、答完后何时再来，也无法看到完整的复习进度。

### P2：题目内容和解析仍依赖文本约定

网页端和 Android 端都需要从 `question` 字符串中解析选项和解析文本。AI 题目格式稍有变化，就可能出现题干为空、选项识别失败或答案解析展示不一致。后端返回的 `explanation` 目前还会从题目文本中抽取，而不是稳定的结构化字段。

### P2：提醒、每日队列和卡片排期是三个相邻但未完全统一的概念

系统同时存在卡片 `nextReviewTime`、知识点 `nextReviewTime`、知识点指定提醒和每日通知任务。它们服务于不同场景，但用户界面容易把它们都理解成“今天要复习的内容”。当前需要明确哪一个是队列真相，哪一个只是通知。

## 7. 目前可以对外说明的业务规则

在不改变代码前，团队可以把当前复习定义为：

1. 只有已登录用户才能查询和提交复习；工作区由当前 JWT 上下文决定。
2. 知识点是否纳入复习由 `needReview` 控制，但它不是复习队列本身；真正决定答题记录的是复习卡片或个人副本。
3. 工作区卡片优先采用题目池模板 + 用户个人副本；个人空间可以直接使用个人副本；历史卡片仍从旧表兼容读取。
4. 复习提交是一次不可忽略的业务事件，会更新进度、写日志、触发积分，并尝试更新下一次复习时间。
5. “今天待复习”应该按用户、工作区、未归档/未删除、已到期的个人卡片计算；当前代码还没有把这条规则在所有入口统一落实。
6. 复习统计应以 `review_log` 为主要事实来源，卡片上的累计字段用于当前进度和兜底；当前代码已经部分采用这个方向，但新旧表相加仍需治理。

## 8. 后续重构时的优先顺序

这次梳理不直接修改实现，建议后续按下面顺序收口：

1. **先定义唯一队列规则**：明确 `status`、`nextReviewTime`、`isArchived/deleted` 的职责，确定“到期卡片”的唯一 SQL 条件。
2. **再统一数据访问层**：由一个 ReviewCardRepository/查询服务隐藏旧表兼容逻辑，避免 Controller、统计、定时任务各自拼新旧查询。
3. **统一提交结果契约**：返回结构化题型、正确答案、解析、下一次复习时间、掌握度和本次统计，网页和 Android 不再自行猜测文本格式。
4. **把复习会话与队列快照分开**：开始一轮复习时固定卡片 ID 列表，提交后只更新单卡结果；本轮结束或重新进入时再刷新队列。
5. **补齐认证和工作区失败态**：401 必须显示“登录已过期并引导重新登录”，工作区切换后必须等待新 token 生效再拉复习数据。
6. **补齐跨端验收**：至少验证个人空间、工作区、旧卡片、新副本、答对、答错、到期重新出现、重复提交、token 过期和切换工作区。

## 9. 建议的验收场景

| 场景 | 应验证的事实 |
|---|---|
| 新用户登录后打开复习 | token 有效，返回当前空间的卡片或明确空态 |
| token 过期后打开复习 | 两端均显示登录失效，不显示“没有卡片” |
| 个人空间生成卡片 | 个人副本可查询、可提交、可再次排期 |
| 工作区生成卡片 | 题目池有模板，创建者有个人副本，成员加入后有独立进度 |
| 答对一次 | 日志、次数、正确数、掌握度、下一次时间均更新 |
| 答错一次 | 错误数增加，下一次时间按缩短规则计算 |
| 到期后再次查询 | 卡片按唯一到期规则重新进入队列 |
| 网页提交后继续本轮 | 当前题目结果和队列快照不跳变 |
| Android 提交后重新进入 | 与网页看到同一张卡片的状态和排期 |
| 多端交替复习 | 统计以服务端日志为准，不重复计数 |

## 11. 复习领域规则澄清

下面是围绕复习业务需要先统一的产品规则。这里将“当前代码行为”和“建议作为统一规则的目标行为”分开，避免把设计意图误认为已经完成。

### 11.1 复习和知识管理的关系

知识管理负责保存用户认为有长期价值的内容；复习负责把这些内容转化成可执行、可排期、可追踪的学习任务。二者不是两套互相独立的内容系统，而是同一条链路上的不同层次：

| 层次 | 业务对象 | 责任 |
|---|---|---|
| 内容层 | `knowledge_node` | 保存标题、摘要、正文、来源、工作区归属和知识状态 |
| 复习意图层 | `needReview` | 表达用户是否希望这个知识点进入复习体系；它不是“今天到期”的判断 |
| 练习层 | `review_card_pool` / `review_card` | 保存题目、选项、答案、解析、题型和难度 |
| 个人计划层 | `user_review_card` | 保存某个用户对某张题目的独立进度和排期 |
| 事件层 | `review_log` | 记录每一次提交的结果和耗时，是统计和审计的事实来源 |

推荐把关系定义为：

```text
知识点是学习内容
复习卡片是知识点的练习投影
个人复习副本是用户的学习计划
复习日志是不可变的学习事件
知识点掌握度是卡片事件聚合后的摘要
```

这意味着：

- 用户编辑知识正文时，不应该静默修改已有的个人复习进度；应标记“内容版本发生变化”，由产品决定是否重新生成或提示复习。
- `needReview=1` 只表示纳入复习范围，真正的待复习队列必须由个人复习副本的有效状态和 `nextReviewTime` 决定。
- 知识点可以没有复习卡片，也可以有多张卡片；一张卡片不应该反过来成为知识正文的唯一来源。
- 知识点的 `masteryLevel` 是面向知识的汇总指标，卡片的 `masteryLevel` 是面向题目的指标，二者不能混作同一个字段展示。

### 11.2 排期算法：当前实现与应统一的规则

当前实现使用艾宾浩斯式固定间隔：默认 `[1, 7, 14, 30, 60]` 天；答对选择对应阶段的间隔，答错使用当前间隔的一半但不低于 1 天。用户偏好允许自定义 3～8 个递增间隔，并从下一次答题后生效。

当前存在一个必须先定下来的阶段偏移问题：提交代码先把 `reviewCount` 加 1，再把新的次数传给排期服务。如果新卡片第一次答题时传入的是 1，那么它会直接选用数组第 1 项（7 天），而不是第 0 项（1 天）。文档中“第 0 次后 1 天”的描述与提交时的实际计数时机不一致，必须通过单元测试固定下来。

建议统一成以下规则：

1. 新卡片 `nextReviewTime` 为当前时间，允许立即开始第一轮。
2. 第一次答对后安排 1 天；之后依次为 7、14、30、60 天，超过最后阶段后保持最后阶段。
3. 答错不改变累计复习次数的事实，但将下一次安排为 1 天或当前阶段的一半，取较大的值；连续答错是否进一步缩短，需要单独定义，不能由前端猜测。
4. 到期条件唯一写成 `active && isArchived=false && nextReviewTime <= now`。掌握度高不代表永久移出队列。
5. `status` 只描述卡片生命周期，例如 `active / suspended / archived`；不能同时承担“本轮是否完成”和“是否已经掌握”两种语义。
6. 提交必须以服务端时间为准，客户端只上报耗时；跨网页端和 Android 端统一使用同一时区策略。
7. 同一张卡片的重复提交要有幂等策略。已处理的提交不能因为网络重试再次增加次数或积分。

排期算法后续可以再做自适应，但第一阶段应先保证固定间隔、到期判断、状态字段和重复提交在两个端完全一致。

### 11.3 复习题质量怎么把控

当前代码主要依赖 AI 生成文本，服务端对答案做字符串比较，网页端和 Android 端再从题目文本解析选项和解析。题目质量反馈接口目前更接近记录日志，尚未形成发布前校验、题目版本和淘汰机制。

建议把质量拆成四道门：

**第一道：结构合法性。** 生成结果必须是结构化数据，而不是把题干、选项、正确答案和解析拼在一段文本中。最少应包含 `cardType`、`stem`、`options`、`correctAnswer`、`explanation`、`sourceNodeId`、`sourceVersion` 和 `difficulty`。选择题的正确答案必须是现有选项之一，填空题和简答题需要明确判定方式。

**第二道：知识依据。** 题目、答案和解析必须能够回指到知识点正文或明确来源。无法从来源推导出的内容应进入待审核状态，不应直接出现在正式复习队列中。

**第三道：生成后校验。** 至少检查：题干是否为空、答案是否缺失、解析是否支持答案、选项是否重复、答案是否泄露在题干中、题目是否与同知识点已有题目高度重复。AI 生成器和校验器应是两个独立步骤，校验失败时重试次数必须有限并留下失败原因。

**第四道：使用反馈。** 用户提交后可以标记“答案有误、题目不清、难度不合适、与知识无关”。低质量题目进入 `draft/review/retired` 流程；工作区 owner 可以编辑题目池模板，但已经开始答题的个人副本要保留题目版本，避免历史结果被静默改写。

建议的质量状态为：

```text
generated → validated → published → questioned → retired
```

第一阶段的验收标准应包括：没有正确答案的题目不能发布；解析不能与答案矛盾；题目必须显示来源知识点；用户反馈能够定位到题目版本；题目被下线后不能再进入新用户的复习队列。

### 11.4 非个人空间的工作区复习

工作区复习应采用“共享内容、个人进度”的规则：

```text
工作区知识点
      ↓ 生成一次
工作区题目池模板
      ↓ 用户主动加入
用户个人复习副本
      ↓ 独立答题和排期
用户自己的复习日志、掌握度和下次时间
```

推荐规则如下：

- 工作区成员默认可以浏览有权限的题目池，但不会自动加入所有题目。
- 用户点击“加入复习”后创建个人副本，初始 `reviewCount=0`，首次复习立即可做。
- 个人副本的答题次数、正确率、掌握度、排期和归档状态完全独立；一个成员答对不会改变其他成员的排期。
- 同一用户重复点击“加入复习”应保持幂等；如果用户想重新开始，应提供明确的“重新开始”操作，而不是让普通加入动作隐式归档旧副本。
- 题目池 owner 可以编辑或下线模板。编辑生成新版本；已经开始复习的个人副本保留原版本，新加入用户使用新版本。
- 工作区成员退出、权限撤销或知识点不再对其可见时，个人副本停止进入队列，但历史日志仍保留用于审计和统计隔离。
- 工作区复习统计默认只统计当前用户自己的副本；社区标签可以聚合工作区成员的匿名汇总，但不能暴露个人答题细节。
- 从工作区复制到个人空间应是显式动作，不能因为切换空间而让同一张卡片自动出现在个人队列中。

当前题目池 PRD 已经覆盖了“模板 + 个人副本”的基本方向，但还需要补充题目版本、加入幂等、成员退出、权限撤销和模板下线后的行为。

### 11.5 需要产品先确认的四个决策

以下决策会直接影响数据库字段、接口契约和网页/Android 的验收，建议在编码前固定：

| 优先级 | 决策 | 推荐默认值 |
|---|---|---|
| P0 | 第一次答对后的间隔到底是 1 天还是 7 天 | 1 天；按“本次答题前的阶段”取间隔 |
| P0 | 已掌握卡片是否继续按到期时间复习 | 继续复习；掌握度不等于移出队列 |
| P0 | 工作区成员是否自动获得全部题目 | 不自动；成员主动加入 |
| P0 | 普通重复加入是否创建新副本 | 幂等返回已有副本；“重新开始”单独操作 |
| P1 | 知识正文修改后旧题目如何处理 | 新建题目版本，旧副本保留历史 |
| P1 | 简答题如何判定正确 | 第一阶段人工/AI 评分并记录评分依据，不使用简单字符串相等 |
| P1 | 题目质量反馈谁负责处理 | 个人空间由用户自处理，工作区由 owner/管理员处理 |
| P2 | 是否根据用户表现动态调整间隔 | 先固定算法稳定运行，再基于日志评估自适应算法 |

### 11.6 对应的最小验收闭环

复习规则确定后，至少要能验证以下场景：

- 知识点不纳入复习时，不生成个人复习任务；纳入后生成题目并可立即开始。
- 个人空间和工作区的知识权限不会互相串数据。
- 工作区成员加入同一题目后，各自答题不会改变他人的排期。
- 第一次答对、连续答对、答错、连续答错的下一次时间符合固定表格。
- 到期前不会出现在“今日待复习”，到期后一定出现。
- 答题网络重试不会重复增加复习次数、积分和日志。
- 题目缺少答案、解析矛盾或来源不存在时不能进入正式队列。
- 题目被编辑或下线后，已有个人副本和历史日志仍能解释当时的答题结果。
- 网页端和 Android 端针对同一用户、同一工作区看到相同的队列和排期。
