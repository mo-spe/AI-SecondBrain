> 版本：V1.0  
> 日期：2026-09-03  
> 状态：MVP 第二阶段已实现，待数据库迁移与联调  
> 来源：`docs/需求池.md` #2  
> 依赖：多用户数据隔离、现有知识广场、通知与内容治理能力

---

## 1. Executive Summary

### Problem Statement

大学生的现实社交范围通常受院校、专业和熟人圈限制，难以发现校内外在特定知识领域真正有经验、且愿意交流的人。现有知识广场已经支持知识文章、点赞、收藏、评论和举报，但内容缺少真实问题的组织，用户也无法沿着优质贡献持续识别并关注值得认识的人。

### Proposed Solution

在现有知识广场之上建设“问题驱动的知识社区”：用户可以公开提问，其他用户可以撰写回答，并主动引用或附带自己明确授权公开的知识点；系统基于回答、收藏、点赞、采纳和关注等可信行为形成领域贡献数据，支持按学校、专业、知识领域和时间范围发现贡献者，最终形成“问题 → 优质知识 → 贡献者主页 → 关注”的连接闭环。

用户默认以昵称参与社区，可通过学校邮箱优先完成校园认证；没有学校邮箱时可提交证明人工审核。用户自行决定是否公开学校、专业和年级信息。MVP 只验证人物发现与关注，联系请求、站内私信和联系方式授权在后续阶段交付。

### Success Criteria

MVP 上线后按连续四周的滚动数据评估：

| 指标 | 目标 | 口径 |
|------|------|------|
| 内容促成关注率 | 每周至少 15% 的社区活跃用户关注过一名通过内容首次发现的用户 | 首次访问路径包含问题、回答或知识文章，且 7 天内关注 |
| 内容到主页转化率 | 每 100 次优质内容详情浏览产生至少 5 次作者主页访问 | 去重用户维度统计 |
| 主页到关注转化率 | 每 100 次作者主页访问产生至少 15 次关注 | 去重用户维度统计 |
| 问题有效回答率 | 至少 30% 的公开问题在 72 小时内获得一条有效回答 | 非删除、非折叠、正文达到最低质量规则 |
| 社区安全 | 经确认的严重骚扰或隐私泄露事件为 0 | 举报与管理员处置记录 |

预算、研发人数和期望上线日期当前为 `TBD`，进入开发排期前由产品负责人补充。

## 2. User Experience & Functionality

### User Personas

| 用户角色 | 典型场景 | 核心诉求 |
|----------|----------|----------|
| 提问者 | 遇到课程、科研、竞赛、实习或技术难题 | 得到有依据的回答，并找到真正懂这个领域的人 |
| 知识贡献者 | 已经积累笔记、知识点或实践经验 | 低成本复用自己的知识，建立可信的专业影响力 |
| 人物探索者 | 想认识本校、目标学校或某领域优秀同学 | 通过真实贡献判断对方是否值得关注，而非只看自我介绍 |
| 校园认证用户 | 希望证明院校身份但保留隐私 | 获得可信标识，并自主决定公开哪些校园资料 |
| 社区管理员 | 处理垃圾内容、冒充认证、骚扰和刷量 | 获得可追踪、可申诉的治理工具 |

### Core User Flow

```text
用户发布公开问题
    ↓
其他用户撰写回答
    ├── 直接回答
    └── 引用/附带经确认公开的个人知识点
    ↓
社区通过点赞、收藏、采纳和举报反馈质量
    ↓
用户查看回答者主页、领域贡献与校园认证
    ↓
关注贡献者
    ↓
后续阶段：发送联系请求 → 对方接受 → 私信或授权联系方式
```

### User Stories & Acceptance Criteria

#### US-1：发布和管理问题

作为提问者，我希望发布带有领域标签的问题，以便让可能掌握相关知识的人看到。

验收标准：

- 支持标题、问题描述、知识领域标签和可选学校范围；标题与正文均有明确长度限制。
- 发布范围支持“全平台”和“仅本校”；选择仅本校时要求用户已完成校园认证。
- 作者可以补充、关闭或删除问题；已有回答后编辑必须保留修改标识。
- 问题详情展示回答数、关注数、浏览数、发布时间和当前状态。
- 用户可关注问题，并在出现新回答或回答被采纳时收到现有通知中心消息。

#### US-2：回答问题并引用知识点

作为知识贡献者，我希望撰写回答并引用自己的知识点，以便复用已有积累并提供可验证的知识依据。

验收标准：

- 回答支持 Markdown 正文，并可附带零个或多个知识点引用。
- 选择知识点时必须展示公开预览和明确授权操作，私有知识不会因被选择而自动公开。
- 被引用知识以发布时快照或已公开版本展示，后续私有编辑不得静默改变历史回答含义。
- 回答作者可编辑和删除自己的回答；编辑后显示“已编辑”。
- 提问者可采纳一条回答；问题允许继续接收其他回答。
- 回答支持现有点赞、收藏、评论和举报能力，重复操作保持幂等。

#### US-3：浏览和发现内容

作为学习者，我希望按领域、学校和热度浏览问题及回答，以便找到与我相关的知识和贡献者。

验收标准：

- 社区首页提供“推荐、最新、待回答、关注”内容流。
- 支持按知识领域筛选；已认证用户可切换“本校”，也可主动选择其他学校。
- 排序不得仅使用总点赞数；至少综合内容质量、时效性、互动可信度和用户兴趣。
- 新用户或低粉丝用户的高质量内容必须拥有基础曝光机会。
- 被删除、审核折叠或无权限内容不能出现在公开流、榜单和搜索结果中。

#### US-4：查看可信个人主页

作为人物探索者，我希望通过个人主页了解一名用户持续贡献的领域和质量，以便判断是否关注。

验收标准：

- 主页展示昵称、头像、简介、可选校园信息、认证状态、擅长领域、关注数和粉丝数。
- 用户可分别控制学校、专业、年级和外部联系方式是否公开。
- 主页展示公开回答、公开知识文章、获赞、获收藏、被采纳和领域贡献摘要。
- 未认证用户不得显示认证徽章；认证状态撤销后徽章即时失效。
- 访问者能够从内容详情进入作者主页，并在主页或内容卡片上关注/取消关注。

#### US-5：关注与贡献者发现

作为学习者，我希望关注持续输出高质量内容的人，并发现某个领域值得认识的贡献者。

验收标准：

- 关注是单向关系，不需要对方批准；支持取消关注、移除粉丝和拉黑。
- 关注成功后，关注者可在“关注”内容流看到对方后续公开内容。
- 贡献者榜支持本校、专业、知识领域及近 7 天/30 天等筛选，不提供单一永久全站总榜作为默认入口。
- 排名使用综合贡献分，不直接公开精确算法权重；用户可看到构成解释，例如“Java 领域近30天 5 条回答被收藏”。
- 自赞、自收藏、已判定异常账号互动和短时间刷量不计入贡献分。

#### US-6：校园身份认证

作为学生，我希望在不强制实名展示的前提下证明学校身份，以提高交流可信度。

验收标准：

- 优先支持学校邮箱验证码认证；无法使用学校邮箱时支持提交证明材料人工审核。
- 认证申请展示材料用途、保存期限和隐私说明，并要求用户明确同意。
- 人工审核材料在审核完成或申诉期结束后删除，只保留学校、认证状态、认证方式、审核时间和必要审计记录。
- 用户默认展示昵称；真实姓名、学号、证件号码和认证原图永不公开。
- 支持认证失效、撤销、重新认证和冒充举报。

#### US-7：内容与关系安全

作为社区用户，我希望屏蔽骚扰者并举报不当内容，以便安全参与讨论。

验收标准：

- 问题、回答、评论、用户主页均提供举报入口。
- 用户可拉黑其他用户；拉黑后双方不能关注，后续阶段也不能发送联系请求或私信。
- 管理员可执行折叠、下架、账号限制、认证撤销和申诉处理，并保留审计记录。
- 对疑似刷赞、刷收藏、批量关注进行限流和异常标记，异常互动不进入榜单计算。

### Contribution Score

贡献分用于“发现值得关注的人”，不等同于学术能力或人格评价。MVP 建议采用可配置、可审计的加权模型：

```text
领域贡献分 = 有效回答质量 + 被采纳 + 有效收藏 + 有效点赞
             + 持续贡献修正 - 举报确认惩罚 - 异常互动降权
```

- 粉丝量仅作为弱信号，不能成为主要排序依据。
- 收藏和采纳权重应高于普通点赞。
- 榜单按领域和时间窗口重新计算，降低先发用户永久垄断。
- 每个榜单必须提供“为什么推荐此人”的可理解说明。
- 具体权重需通过灰度数据校准，首版参数由运营配置，不写死在前端。

### Non-Goals

MVP 明确不建设：

- 联系请求、站内私信、群聊、语音或视频聊天。
- 用户任意私信陌生人，或默认公开微信、手机号等外部联系方式。
- 实时多人协同编辑知识点；该能力仍由原协作共享知识库方案管理。
- 付费问答、知识付费、广告和创作者分成。
- 仅按粉丝量排列的永久全站“名人榜”。
- 自动把用户私有知识库内容发布到社区。
- 用 AI 自动代替用户发布回答或伪造校园认证。

## 3. AI System Requirements

### Tool Requirements

MVP 不依赖新的 Agent 或 RAG 实现，优先复用现有知识搜索、标签、知识广场和 AI Model Client。AI 仅作为辅助能力：

- 问题发布时建议知识领域标签和相似问题，减少重复提问。
- 回答编辑时提示可能可引用的个人知识点，但必须由用户主动选择并确认公开。
- 辅助识别广告、辱骂、个人敏感信息和低质量灌水，结果只作为审核信号。
- 为推荐流生成候选或兴趣标签时，不得直接读取用户未授权公开的私有知识正文。

### Evaluation Strategy

| 能力 | 评估集 | 上线门槛 |
|------|--------|----------|
| 相似问题检测 | 至少 300 对人工标注的问题对 | Precision >= 90%，Recall >= 75% |
| 标签建议 | 至少 200 个跨领域问题 | Top-3 命中率 >= 85% |
| 内容风险辅助识别 | 至少 500 条含正常、广告、辱骂、隐私样本 | 严重风险 Recall >= 95%，正常内容误杀率 <= 3% |
| 知识点建议 | 至少 100 组用户问题与个人知识点集合 | Top-5 有效建议率 >= 70% |

AI 判断不能直接完成封禁或认证拒绝；高风险操作必须由规则或管理员复核。所有 AI 建议应允许用户忽略，且不得展示模型 Chain-of-Thought。

## 4. Technical Specifications

### Architecture Overview

```text
社区前端
  ├── 问题流 / 问题详情 / 回答编辑器
  ├── 用户主页 / 关注列表 / 贡献者榜
  └── 校园认证 / 隐私设置
          ↓
现有 Spring Boot 应用
  ├── CommunityQuestion / CommunityAnswer
  ├── KnowledgeShare（知识公开快照或现有广场发布记录）
  ├── UserFollow / UserProfile / CampusVerification
  ├── ContributionRanking
  └── 复用 SquareLike、SquareBookmark、SquareComment、Notification、Report
          ↓
MySQL + 现有搜索/缓存/通知基础设施
```

不得重复实现现有 RAG、Elasticsearch、知识图谱、AI Model Client、点赞、收藏、评论、通知和举报能力。进入技术设计前，需要先确认现有 `SquarePost` 是否扩展为多内容类型，或抽取统一互动目标模型；未经确认不得直接修改已有数据库表。

### Core Domain Model

| 概念 | 关键数据 | 业务约束 |
|------|----------|----------|
| Question | 作者、标题、正文、范围、学校、标签、状态、采纳回答 | 仅本校范围要求已认证；关闭后默认不再接收回答 |
| Answer | 问题、作者、正文、编辑状态、采纳状态 | 每名用户可多次编辑；删除采用逻辑删除 |
| AnswerKnowledgeReference | 回答、知识来源、公开快照/发布版本 | 必须经过知识所有者显式授权，不允许直接暴露私有节点 |
| UserProfile | 昵称、头像、简介、擅长领域、各资料可见性 | 隐私字段独立控制，不以一个总开关替代 |
| CampusVerification | 用户、学校、方式、状态、审核与过期信息 | 原始材料限期删除；认证结果可撤销 |
| UserFollow | 关注者、被关注者、状态、创建时间 | 唯一关系；禁止自关注；拉黑优先于关注 |
| UserBlock | 发起人、目标用户、创建时间 | 生效后取消双方已有关注并阻断新关系 |
| ContributionSnapshot | 用户、领域、时间窗口、分数组成 | 可重算、可审计，不作为永久声望资产 |

### Integration Points

建议的产品级 API 边界如下，具体字段在 API 设计阶段确定：

| 模块 | 接口方向 |
|------|----------|
| 问题 | 发布、列表、详情、编辑、关闭、删除、关注问题 |
| 回答 | 发布、编辑、删除、采纳、引用知识点 |
| 社区互动 | 复用或扩展现有点赞、收藏、评论、举报接口 |
| 人物关系 | 关注、取消关注、粉丝列表、关注列表、拉黑 |
| 用户主页 | 公开资料、公开贡献、领域摘要、隐私设置 |
| 校园认证 | 邮箱认证、材料申请、审核、撤销、状态查询 |
| 贡献者发现 | 按学校、专业、领域和时间窗口查询榜单 |
| 通知 | 复用现有通知中心承载新回答、采纳、关注和审核结果 |

### Security & Privacy

- 私有知识默认不可见。附带知识点必须经过逐次预览和公开确认，撤销公开后保留回答必要快照还是隐藏引用，需在技术设计中形成可审计规则。
- 学校认证材料属于高敏感数据，必须加密传输、限制管理员访问、记录审计日志并执行自动删除。
- 不公开学号、证件号、认证原图、手机号和真实姓名；学校、专业、年级由用户分字段控制可见性。
- 所有创建、编辑、采纳、关注、拉黑和审核接口执行身份与资源归属校验，并具备幂等和频率限制。
- 排名系统排除本人互动、已封禁账号互动和风险流量；关键分值变化保留来源，便于申诉。
- 推荐系统提供“减少此类内容”“不看此用户”和拉黑能力，避免因个性化推荐形成持续骚扰。
- 面向所有学校开放时，需要建立学校标准名称库、认证域名配置和同名学校消歧机制。

### Non-Functional Requirements

| 项目 | 要求 |
|------|------|
| 性能 | 社区流、问题详情和用户主页接口 P95 <= 500ms；榜单接口 P95 <= 800ms，可使用缓存 |
| 一致性 | 点赞、收藏、关注和采纳操作幂等；计数器可最终一致，但明细关系为事实来源 |
| 可用性 | 核心浏览和回答流程月可用性 >= 99.9% |
| 可观测性 | 记录发布、回答、内容到主页、主页到关注的漏斗事件，并区分推荐来源 |
| 可访问性 | 键盘可完成发布、回答、关注和举报主流程；重要状态不只依赖颜色表达 |
| 治理时效 | 严重隐私/骚扰举报进入高优先级队列；具体处理 SLA 在运营策略评审时确定 |

## 5. Risks & Roadmap

### Phased Rollout

#### 当前实施状态（2026-09-03）

MVP 第一、二阶段已完成代码实现：

- 新增公开问题列表、关键词检索、“最新/待回答”筛选、问题发布和详情浏览。
- 新增 Markdown 回答、最多 5 个个人知识点选择、发布时公开快照和隐私提示。
- 新增问题作者采纳回答，并复用现有通知中心发送“新回答”和“回答被采纳”通知。
- 新增 `/community` 前端入口，采用内容优先的编辑式布局，并完成键盘操作、焦点状态、移动端和减少动效适配。
- 数据库采用新增 `community_question`、`community_answer` 两张领域表，不修改现有 `square_post` 及互动表。
- 新增独立社区资料、关注与拉黑关系，不向现有账户表写入社区专属字段。
- 新增公开个人主页、社区资料编辑、粉丝/关注列表、关注与取消关注、拉黑与解除拉黑接口。
- 公开主页仅输出昵称、头像、公开简介、领域标签、关系状态、聚合贡献和最近公开内容，不包含邮箱、手机号、密码或 API Key。
- 问题列表、问题详情与回答作者均可进入 `/community/users/:id`，返回后恢复问题筛选、详情和滚动位置。
- 个人主页采用编辑式双栏结构，支持本人、他人和拉黑三种状态；移动端优先展示身份、关注操作与高价值贡献数据。
- 社区接口已加入现有 JWT 拦截路径，确保 `/api` 上下文路径下发布问题、回答和用户关系操作均能获得当前用户身份。

本阶段尚未包含校园认证、贡献者榜、联系请求、私信以及问题/回答的点赞收藏；这些仍属于后续 MVP 工作，而不是已交付能力。执行联调前需依次应用 `V10__add_community_questions.sql` 和 `V11__add_community_profiles_and_follows.sql`。

#### MVP：知识促成人物发现

- 公开/本校问题、回答、回答采纳和问题关注。
- 回答正文引用或附带经用户确认公开的知识点。
- 昵称型个人主页、分字段校园资料可见性。
- 学校邮箱优先、材料人工审核兜底的校园认证。
- 单向关注、粉丝/关注列表、拉黑。
- 按学校、专业、领域和时间窗口发现贡献者。
- 复用现有点赞、收藏、评论、通知、举报和管理能力。
- 建立“内容浏览 → 主页访问 → 关注”的增长漏斗。

#### V1.1：连接意愿验证

- 联系请求及接受、拒绝、撤回和频率限制。
- 联系请求必须携带来源内容和简短说明，帮助接收者判断价值。
- 双方建立联系后允许使用站内文字私信。
- 用户可按联系人或所有人关闭联系请求。

#### V1.2：安全沟通与联系方式授权

- 私信会话、未读消息、拉黑、举报和反骚扰限制。
- 用户按联系人授权展示微信、邮箱等外部联系方式，默认全部关闭。
- 联系质量反馈与安全治理，但不公开展示私人交流评分。

#### V2.0：社区质量与规模化

- 推荐模型和贡献分实验平台。
- 领域社区、专题问答和校园活动。
- 专家认证、导师/学长学姐意愿标签。
- 在验证真实需求后评估协作问答、悬赏或知识服务，需单独立项。

### Technical Risks

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 社区冷启动，问题无人回答 | 用户快速流失 | 首批聚焦高频校园领域；待回答流；邀请已有知识贡献者；不过早铺开大量空频道 |
| 粉丝与榜单诱发刷量 | 推荐失真、社区攀比 | 粉丝弱权重；收藏/采纳高权重；异常互动降权；领域与时间窗口榜单 |
| 私有知识被误公开 | 严重隐私事故 | 明确预览和二次确认；使用公开快照；默认不授权；提供撤销和审计 |
| 校园认证材料泄露 | 法律与信任风险 | 最小化采集、加密、访问审计、限期删除、优先学校邮箱 |
| 陌生人联系演变为骚扰 | 用户安全受损 | MVP 不开放私信；后续使用联系请求、权限设置、限流、拉黑和举报 |
| 内容质量被热度绑架 | 专业用户离开 | 综合质量信号、新内容探索、反刷量、推荐原因解释和人工治理 |
| 现有知识广场模型难以扩展 | 重复表和互动逻辑 | 技术设计阶段先评估多内容类型与统一互动模型，不在 PRD 阶段直接改表 |
| 推荐形成校园或专业信息茧房 | 限制跨圈连接 | 默认提供本校与全平台切换，允许主动浏览其他学校和领域 |

### Release Gates

进入 MVP 开发前必须完成：

1. 确认产品负责人、研发资源、预算和目标上线日期。
2. 完成现有知识广场数据模型复用评审，决定问题/回答的互动如何接入。
3. 完成知识点公开快照与撤销规则设计，确保 Research Agent 和社区都不能自动修改或发布用户知识库。
4. 完成校园认证隐私影响评估、材料删除策略和管理员审核权限设计。
5. 完成社区治理规则、举报分类、处罚和申诉流程。
6. 建立 MVP 指标埋点方案和基线数据，确保上线后可以判断是否真的促成有价值连接。

### Open Decisions

以下内容不阻塞需求确认，但必须在设计或排期阶段确定：

- MVP 首批重点知识领域与冷启动学校范围。
- 学校认证有效期和人工审核 SLA。
- 知识点撤销公开后，历史回答中的引用采用隐藏、匿名快照还是保留授权版本。
- 贡献分初始权重、榜单刷新频率与异常流量阈值。
- 举报处理 SLA、申诉期限和管理员分级权限。
- 研发预算、团队规模与上线日期。
