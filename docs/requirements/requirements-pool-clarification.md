## 需求 #1：多用户数据隔离与管理员管控

**状态：可以做了 | 优先级：P0**

### 澄清问题

| # | 问题 | 优先级 |
|---|------|--------|
| 1 | **租户模型粒度**：每个注册用户一个独立空间，还是允许创建团队 workspace？直接影响数据库 schema 设计 | 高 |
| 2 | **管理员定义**：系统级超级管理员还是用户自行管理？管理员能否查看用户私有知识卡片？ | 高 |
| 3 | **RBAC 角色列表**：目前只提了"管理员"，具体角色是 Admin/Editor/Viewer 还是更细？角色与租户的关系？ | 中 |
| 4 | **数据隔离方案**：应用层多租户（tenant_id）、数据库层隔离（独立 schema）、还是独立数据库？成本差异大 | 中 |
| 5 | **内容审核方式**：敏感词过滤、人工审核队列、还是自动举报机制？ | 低 |

### 用户故事

| ID | 描述 | 验收标准 |
|----|------|---------|
| US-1.1 | 作为管理员，创建和管理用户账号 | 后台可创建/禁用/删除用户；禁用后用户无法登录 |
| US-1.2 | 作为用户，只能看到自己创建的知识卡片 | 用户 A 请求用户 B 的知识点接口返回 403 |
| US-1.3 | 作为管理员，查看系统用户数和资源使用 | Dashboard 展示用户数、知识点数、存储容量 |

### 风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| 后期给已有数据加 tenant_id 迁移成本高 | 高 | 数据库 schema 一次性设计到位 |
| RBAC 设计过重导致周期过长 | 中 | V1 只做 Admin + User 两种角色 |

## 需求 #2：协作共享知识库

**状态：需要想想 | 优先级：P2**

### 头脑风暴 — 5W1H

| 维度 | 分析 |
|------|------|
| Who | 同一团队/学习小组的用户、知识创作者和消费者 |
| What | 用户把知识库分享给其他人，支持查看或协作编辑 |
| When | 用户创建知识库后，需要分享给团队成员时 |
| Where | 知识库详情页 → 分享设置面板 |
| Why | 知识孤岛问题，目前每人只能管理自己的知识 |
| How | 分享链接 + 权限控制（V1 不做实时协同编辑） |

### 澄清问题

| # | 问题 | 优先级 |
|---|------|--------|
| 1 | **共享粒度**：知识库级别还是知识点级别？建议 V1 只做知识库级别 | 高 |
| 2 | **多人编辑冲突处理**：last-write-wins、OT 算法、还是 CRDT？建议 V1 用编辑锁或无冲突处理 | 高 |
| 3 | **分享方式**：链接分享（简单）还是指定用户搜索（需用户选择 UI）？ | 中 |
| 4 | **是否需要版本历史？** 需要则大幅增加复杂度 | 中 |

### 用户故事

| ID | 描述 | 验收标准 |
|----|------|---------|
| US-2.1 | 作为知识库所有者，通过链接分享知识库 | 生成分享链接，可设置"仅查看"或"可编辑"权限 |
| US-2.2 | 作为被分享者，接受邀请后访问共享知识库 | 打开链接 → 确认加入 → 在列表中看到共享知识库 |
| US-2.3 | 作为所有者，随时取消分享或修改权限 | 在分享设置面板可修改/撤销某个用户的权限 |

### 风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| 实时协作实现周期失控 | 高 | V1 只做按知识库分享，无实时编辑 |
| 权限模型随需求膨胀 | 中 | 只做 Owner/Editor/Viewer 三层 |

## 需求 #3：社交功能（评论/点赞）

**状态：需要想想 | 优先级：P3**

### 头脑风暴 — 反向思考

> 如果没有评论功能，用户会流失吗？知识管理工具的核心竞争力是知识组织和检索，社交是增强功能。但完全没有互动则用户间只能通过外部渠道交流，不利于社区氛围。

### 澄清问题

| # | 问题 | 优先级 |
|---|------|--------|
| 1 | **评论对象**：知识卡片、知识库、还是都可以？决定后端模型复杂度 | 高 |
| 2 | **内容可见性是一个被隐藏的独立需求**：公开/好友/私密三种可见性模型应该单独列为需求 | 高 |
| 3 | **通知范围**：站内通知 + 邮件 + 推送？V1 建议只做站内通知 | 中 |
| 4 | **用户关系模型**：关注（单向，简单）还是好友（双向确认）？ | 中 |

### 用户故事

| ID | 描述 | 验收标准 |
|----|------|---------|
| US-3.1 | 作为用户，在知识卡片下发表评论 | 知识点详情页底部有评论区，发送后即时显示 |
| US-3.2 | 作为用户，点赞有价值的知识点 | 点击点赞按钮，计数 +1，再次点击取消 |
| US-3.3 | 作为用户，收到评论回复时收到站内通知 | 导航栏通知图标出现红点，点击查看通知列表 |

### 风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| UGC 内容审核合规风险 | 中 | 接入敏感词过滤 + 举报机制，可后置到 V1.1 |
| 通知体量过大 | 低 | 默认只发评论回复通知，其他可订阅 |

## 需求 #4：学习游戏化与参与感

**状态：需要想想 | 优先级：P1**

### 头脑风暴 — 类比思考

| 参考产品 | 核心机制 | 可借鉴 |
|----------|---------|--------|
| Duolingo | 连续打卡 + 宝石奖励 + 排行榜 | 连续打卡的心理锚定效果极好 |
| GitHub 贡献图 | 日历热力图 + streak 计数 | 可视化个人学习轨迹 |
| Notion 进度条 | 百分比进度 | 知识体系掌握度可视化 |
| Strava | 分段排行榜 + 个人纪录 | 与自己比较比与他人比较更有动力 |

### 澄清问题

| # | 问题 | 优先级 |
|---|------|--------|
| 1 | **排行榜范围**：全局榜（新人追不上）还是按知识领域分榜（数据建模复杂但合理）？ | 高 |
| 2 | **成就触发行为**：首次创建知识点、连续 7 天打卡、完成 100 个知识点、图谱超 50 个节点等 | 高 |
| 3 | **打卡粒度**：登录即打卡、学习 N 分钟、还是完成复习任务才算？ | 中 |
| 4 | **断签机制**：是否允许补签？是否需要"请假模式"（参考 Duolingo 冻结机制）？ | 中 |

### 用户故事

| ID | 描述 | 验收标准 |
|----|------|---------|
| US-4.1 | 作为用户，看到每日打卡连续天数 | 每天完成至少 1 个复习任务后自动打卡，主页展示连续天数 |
| US-4.2 | 作为用户，获得成就徽章记录学习里程碑 | 达成条件时弹窗通知，个人主页展示所有徽章 |
| US-4.3 | 作为用户，看到本周/本月排行榜 | 排行榜按复习次数排名，展示 Top 20 |

### 风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| 排行榜数据可刷 | 中 | 只统计复习完成数（难伪造），不统计创建数 |
| 游戏化过度干扰学习 | 低 | 不采用虚拟货币、道具等重度机制 |
